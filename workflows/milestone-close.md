# Milestone close — PmCamp, before declaring a milestone done

Run before telling the user a milestone is done. When Superpowers reaches finishing-a-development-branch, run this before its merge menu, commit this close's doc edits on the branch, and present the verdict with the menu — one user turn for both. On FAIL, don't present the menu: fix or re-plan first. Inputs: the requirements doc, Superpowers' final review, and its "Rulings I made" list.

1. Verify — persona Verification rules (tests incl. impacted callers, `git log`, no stubs).
2. Observe the product (milestones that change observable behaviour; a purely internal change says so in one line and skips this step). Build & run it; a surface that doesn't build or start is not done. Proportionate: one real-path observation per acceptance criterion, through the entry point its user would use — not an exhaustive test pass:
   - Web UI → browser: agent-browser if installed (token-efficient), else Playwright MCP. Walk each primary flow end-to-end; check UI states (empty / loading / error / validation), obvious console errors, and `DESIGN.md` conformance when present. Browser extension → load it unpacked (agent-browser `--extension <path>`).
   - HTTP API → the running server on its real database, not an in-process test client: send the criterion's request (curl; Windows PowerShell 5.1: `curl.exe`), check status + body, then one read-back proving the effect.
   - CLI → the built or installed entry point, run from a clean directory: exit code, stdout / stderr, files written.
   - Mobile → Maestro (`maestro test`, or its `maestro mcp` server), else mobile-mcp, on a simulator / emulator: drive the flow, take a screenshot. iOS needs macOS + Xcode.
   - Background job → trigger it the way production does (API, CLI, queue); observe the effect (DB, queue, logs); trigger it again — no duplicate.
   - Library → install the packed artifact in a scratch directory; run a short consumer script against the public API.
   Never install a surface tool yourself (Maestro, Java, simulators, browsers): name what's missing, give the user a concrete manual checklist for those criteria — they stay ⏳ — and continue. Recurring critical flows may graduate into automated E2E tests once they stabilize — not by default.
   Browser can't open the app while `curl` on this machine gets a response → a loopback mismatch, not an app bug. For this run only and loopback only (on the host never `0.0.0.0` / `::`, which expose it to the network), one try per rung, stop at the first that renders: (1) swap `127.0.0.1` ↔ `localhost` — a Node ≥17 server bound to `localhost` may listen on `::1` only; (2) `http://[::1]:<port>/`, restarting the server on `::1` if it isn't listening there — some browser builds can't reach IPv4 loopback (seen: agent-browser's Chrome for Testing behind a full-tunnel VPN); skip on WSL mirrored networking or with IPv6 off; (3) Playwright MCP, or agent-browser `--executable-path` pointing at an installed Chrome; (4) the manual checklist. No deeper diagnosis. Rebind with flags, never by editing code or config: Vite `--host ::1 --port <p> --strictPort` · Next `-H ::1 -p <p>` · uvicorn / `fastapi dev` `--host ::1 --port <p>` · Django `runserver [::1]:<p>` · fastify-cli `-a ::1 -p <p>` · host set in code (Nest, Express, Fastify) → `HOST=::1` for that run (PowerShell `$env:HOST='::1'`). Through a package script: `pnpm dev --host ::1`; npm needs `npm run dev -- --host ::1`.
   Server and browser in different network namespaces: a server in a container binds `0.0.0.0` inside it (the container's own network) and is published as `-p 127.0.0.1:<p>:<p>` — open the published port; Claude Code inside a devcontainer, Codespace or remote host → the browser tool must run there too. Still unreachable → the manual checklist; never widen a host bind to make a walkthrough work.
3. Trace — one row per acceptance criterion of this milestone, copied from the requirements doc: `| Criterion | Evidence | Status |`. Evidence is concrete: a test that ran green this session (name it) or a step-2 observation and what you saw; a commit hash only for a criterion about the code itself. "Implemented" is not evidence. A unit or in-process test alone never makes a behaviour criterion ✅ — that needs step 2's observation (or an E2E test against the running product). Status: ✅ met (observed) · ⏳ awaiting the user's check · ⚠️ partly · ❌ not met. A defect you hit inside a criterion's own flow (a state it names that breaks mid-flow) marks that criterion ⚠️ or ❌ — not a side note. A ⏳ criterion the user confirms becomes ✅, with their words as the evidence.
4. Verdict — the first that applies:
   - FAIL — any ❌ or ⚠️ not waived. Not done: fix or re-plan.
   - CONCERNS — any ⏳ (a criterion you could not observe yourself stays ⏳ until the user confirms it — never PASS from the checklist alone), or a remaining risk: a parked review finding or ruling that matters, a flaky test. Name each and where it is tracked; re-run the verdict once resolved.
   - WAIVED — every unmet criterion was waived: the user accepted it explicitly, in their own words, this session. Record the criterion, reason, their words and the date next to the criterion in the requirements doc. Never infer a waiver.
   - PASS — every criterion ✅.
5. Record — `docs/STATUS.md`: the milestone collapses to one line, `M<n>: <verdict> (YYYY-MM-DD)` (STATUS's prune rule still applies). An ADR for each non-trivial decision. No new files besides step 6's.
6. `docs/ARCHITECTURE.md` — update only when boundaries or contracts changed; cues from code-review-graph's overview tools (`.claude/rules/core.md`): changed communities, new coupling warnings, new hub/bridge nodes. Missing and the project now has ≥2 domain modules → create it, unless an architecture doc already exists (CLAUDE.md's pointer, or any `architecture*` doc). One without the `Verified at` first line is user-owned: propose changes as a diff; never move, rename, rewrite, or translate it. Content: module map, boundaries, data flow, key contracts, shared hotspots; link `.claude/rules/` + `docs/adr/`, never restate them. First line `Verified at <commit>`; English; ≤80 lines.
7. `/ponytail-review` on the milestone diff — surface its delete-list if any; a prompt to trim, not a gate.
8. Retro — read the requirements doc's `## Retro` first, then add at most 3 lines, only if something happened: `M<n>: broke … · repeated … · change …`. A repeat of an earlier line → Known pitfalls or a mechanical check; a user preference → Working agreements.

Bounded lane: steps 1–2 never skip (step 2: one observation of the changed behaviour); replace 3–4 with one evidence line (what you verified, how, what you observed); skip 5–8 except an ADR for a non-trivial decision and a Retro line if something broke. Any edit to an architecture doc still follows step 6's rules.
